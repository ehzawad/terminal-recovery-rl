## Systems: long-horizon evaluation and training feasibility on one A6000 (transfer-systems)

**Result:** This box can plausibly *evaluate* a pinned, offline-derived Terminal-Bench subset at 32K context. It cannot yet support a credible commitment to four arms, four attempts, 45–100 tasks, and longer-horizon GRPO within 45 A6000 GPU-hours. The two decisive unknowns are external-task wall time and the memory and speed of a real long-trajectory training update. Full offline TB2.1 is not ready; even TBLite’s immediately promising offline-grader pool is only 44 tasks before further admission checks.

**Verified evidence.** The pinned model has a 248,320-token vocabulary and a 262K configured position limit ([config.json](/mnt/sdb/arafat/.cache/huggingface/hub/models--Qwen--Qwen3.5-9B/snapshots/c202236235762e1c871ad0ccb60c8ee5ba337b9a/config.json:58)). The recorded vLLM 0.30 run at `gpu-memory-utilization=0.80` loaded 17.02 GiB of weights and reported 20.29 GiB of KV capacity, or 468,433 cached tokens ([vLLM log](/mnt/sdb/arafat/ehz/llm/terminal-recovery-rl/runs/probe_fifo_runbook/vllm.log:38), [capacity](/mnt/sdb/arafat/ehz/llm/terminal-recovery-rl/runs/probe_fifo_runbook/vllm.log:51)). Dividing that *measured 8K configuration’s* capacity gives a first bound of fourteen full 32K sequences or seven full 64K sequences; it is not a measured long-context throughput result. The host reported 40 logical CPUs, 125 GiB RAM with 96–98 GiB available, and 11 TiB free on the Docker data filesystem. A6000 usage changed from 18 GiB to 22 MiB during this read-only inspection, so an exclusive GPU window must be confirmed at run time. vLLM reserves cache according to its memory setting, and Docker CPU limits are caps rather than reservations ([vLLM configuration](https://docs.vllm.ai/en/latest/api/vllm/config/), [Docker resource constraints](https://docs.docker.com/engine/containers/resource_constraints/)).

**Offline admission is substantial work.** A local manifest scan found 100 TBLite tasks, no prebuilt task images, and 44 grader scripts with no obvious network-install command; 56 grader scripts do install or fetch tools. Forty-one of those 44 omit both CPU and RAM limits, and 40 declare a 3,600-second agent timeout. The “44” is a static screen, not 44 proven runnable offline tasks: images still need pinned builds, and grader, no-op, and reference runs must work with the agent and verifier network disabled. TB2.1 has 89 prebuilt-image references, all 89 declare internet access, and all 89 sampled grader scripts install tooling at grading time; a representative script uses `apt-get`, `curl`, and `uvx` ([task.toml](/mnt/sdb/arafat/ehz/llm/.pools/tb21/tasks/portfolio-optimization/task.toml:23), [test.sh](/mnt/sdb/arafat/ehz/llm/.pools/tb21/tasks/portfolio-optimization/tests/test.sh:3)). None of its `alexgshaw` images appeared in the local Docker image listing. Reaching even 45 admitted external tasks therefore requires at least one verified offline grader adaptation; reaching 100 requires many. Pin image digests and dependency artifacts, and report the resulting score as an **offline-derived subset**, not an official full-suite score. The existing sandbox also forces `/home/user` and its own user setup ([sandbox.py](/mnt/sdb/arafat/ehz/llm/terminal-recovery-rl/termrl/sandbox.py:76)); TB images need their declared workdirs and users preserved.

**Settings to test before freezing the harness.** For evaluation, start with `--max-model-len 32768`, `--gpu-memory-utilization 0.80`, `--max-num-seqs 8`, and **six active attempts**; raise active attempts to eight only after a mixed-task host-load test. Cap cumulative completion *including tool-result tokens* at 24,576, individual model responses at 1,024 generated tokens, and bash calls at 64. A 64K alternative is `--max-model-len 65536`, utilization `0.80`, `--max-num-seqs 4`, **four active attempts**, a 49,152-token cumulative completion cap, and 96 calls. Keep the existing 3,000-character displayed tool-output cap initially. Neither configuration guarantees its call cap is reachable: the current loop ends when cumulative completion or context fills ([rollout.py](/mnt/sdb/arafat/ehz/llm/terminal-recovery-rl/termrl/rollout.py:112)). Long conversations need a specified history-window rule applied identically to P, S, D, and R, or a registered truncation gate. Use `min(600 seconds, remaining agent time)` per command, the task’s declared agent and verifier timeouts, and a hard 120-second allowance for startup and cleanup; prospectively exclude tasks whose declared agent timeout exceeds 3,600 seconds. Count agent and verifier containers together under the eight-container limit. For missing resource declarations, test a fixed **2 CPU/4 GiB** default; retain larger declared limits up to 4 CPU/8 GiB. Admit concurrent tasks only while their summed limits stay at or below **16 CPU and 48 GiB RAM**, with `--memory-swap` equal to the memory limit so the already-full host swap does not become hidden capacity. These are proposed derived-benchmark settings, not measured safe limits.

**Training is the tighter constraint.** The only GRPO smoke generated 16 short trajectories in 699.3 seconds: 43.7 seconds each, with mean completions around 760–893 tokens. It recorded 38.63 GiB sampled device usage, 43.09 GiB peak PyTorch allocation, **zero reward variance, and zero gradients** ([smoke log](/mnt/sdb/arafat/ehz/llm/terminal-recovery-rl/runs/grpo_smoke_v3.log:16)). At that short-run rate, 1,024 trajectories already cost 12.43 hours; a 14-hour R allocation allows only 49.22 seconds per trajectory including updates and waits. Current TRL takes the full completion-token logits path, while the model projects over 248,320 vocabulary entries ([TRL source](/mnt/sdb/arafat/ehz/llm/.venvs/rl/lib/python3.12/site-packages/trl/trainer/grpo_trainer.py:1481), [projection](/mnt/sdb/arafat/ehz/llm/.venvs/rl/lib/python3.12/site-packages/transformers/models/qwen3_5/modeling_qwen3_5.py:1869)). A single 12K-token completion has a 5.68 GiB bf16 logits tensor, or 11.37 GiB at fp32; 24K is 11.37/22.73 GiB. Backpropagation and the PyTorch reference Gated DeltaNet path add memory and compute. Gradient checkpointing and colocated vLLM sleep mode are enabled ([train_grpo.py](/mnt/sdb/arafat/ehz/llm/terminal-recovery-rl/scripts/train_grpo.py:201); [TRL memory guidance](https://huggingface.co/docs/trl/reducing_memory_usage)), but the short smoke leaves no demonstrated margin for long completions. Probe `max-model-len=12288`, `max-completion=8192`, vLLM utilization `0.40`, batch size one, and one **nonzero** update first; only then try 16K/12K. I would not register 32K/24K GRPO on this stack from the present evidence. Short-horizon ET training followed by long-context TB evaluation is executable in principle, but does not establish that R learned long-horizon behavior.

**GPU-hour arithmetic.** Four arms produce 180 episodes for 45 tasks × one attempt, 720 for 45 × four, 400 for 100 × one, and 1,600 for 100 × four. Counting allocated GPU wall time, with ideal six-way concurrency and a hypothetical five-minute *agent-plus-grading* mean, evaluation alone costs **2.5, 10.0, 5.6, and 22.2 hours**, respectively. At ten minutes those become **5.0, 20.0, 11.1, and 44.4 hours**. At four-way concurrency, the 45-task/four-attempt and 100-task/four-attempt ten-minute cases cost **30.0 and 66.7 hours**. Startup, stragglers, incomplete batches, image work, and training are extra. To fit the former seven-hour final-evaluation allowance at eight-way concurrency, the mean complete attempt must be at most **4.67 minutes** for 45 tasks or **2.10 minutes** for 100 tasks with four attempts. The ET mean of 48.9 seconds and roughly 1,201 generated tokens ([summary](/mnt/sdb/arafat/ehz/llm/terminal-recovery-rl/results/gate_headline_v4.summary.json:34)) cannot stand in for these longer TB tasks. This is why four attempts on 100 tasks is especially unlikely to fit the total 45 hours.

**Cheapest settling measurements and open decisions.** Before registration, run outcome-independent checks: inventory every candidate’s image, network calls, declared resources, workdir, and timeout; build or pull a small representative set once; then run its no-op and reference graders with network disabled, logging cold build, warm reset, verifier time, peak CPU/RAM, and whether the grader distinguishes no-op from reference. Separately, use synthetic prompts and mock tool waits—no TB task outcomes—to measure 32K at six/eight streams and 64K at four streams, including actual KV occupancy, prefill/decode throughput, and GPU peak. Finally, run one representative **nonzero-gradient** 8K-completion ET GRPO update, checking total device peak, time, and that an adapter update reaches vLLM; advance to 12K only if it passes. These measurements settle whether to register a small one-attempt transfer pilot, reduce the admitted set, or stop. The owner decision still open is whether a prospectively filtered offline TBLite subset, potentially fewer than 45 tasks and with fewer attempts, is an acceptable external endpoint under the unchanged promotion rule. No benchmark outcomes or training were run for this assessment.
