**Concrete recovery experiment — proposed, not implemented.** The primary task is producing the correct data artifact despite a recoverable local fault. Register one fault per episode, seeded by SHA256 of `recovery-v1 | root_id | episode_seed | family`; choose paths/tools from sorted, per-root audited allowlists. Preserve all original bytes. Apply identical fault assignments and budgets across arms. Record the actual mutation, pre/post hashes, command result and trigger time outside the agent's view. Inject real filesystem/environment changes, never fabricated stderr.

Train on three families: (1) EACCES: remove write permission from the agent-owned output directory or read permission from an agent-owned required input, so chmod can genuinely repair it; (2) ENOENT: move a required input to a seeded discoverable local subdirectory, leaving its bytes intact; (3) unavailable optional tool: remove the designated jq/rsync/gawk executable from that trial's isolated rootfs, while preserving Python/bash/core utilities and a verified alternative solution. No network install is needed or allowed. These are recoverable task disturbances, not random permanent breakage.

Hold out two entire families from training, demonstrations, prompt DEV and reward tuning: (4) blocking I/O: replace a required regular input with a FIFO without a writer, retaining the real bytes in a discoverable backup. The attempted read genuinely blocks; the common tool controller times out after a fixed five seconds and kills the process group. Correct recovery inspects the file and uses/restores valid input; unchanged retries keep failing. (5) ENOSPC: use a small container-local output tmpfs, e.g. 4 MiB, filled by an agent-removable cache file until the designated write actually fails. Recovery frees the disposable space and reruns while preserving source data. Never fill the host filesystem. Held-out-family infrastructure can be smoke-tested with model-free fixtures, without tuning policies on its task traces.

For the controlled mechanism probe, qualify clean tasks by an independently collected, preregistered base-policy 6/8 success criterion. Save a successful clean prefix just before an eligible command. Give every arm the same filesystem snapshot and conversation prefix, inject the fault, execute that same recorded command, then resume the policy from the real error. This equalizes exposure instead of conditioning on errors each policy happened to encounter. Keep this conditional continuation probe separate from from-scratch deployment success. Its final cohort must be frozen without using trained-arm outcomes. In the from-scratch evaluation retain every assigned trial, including fault bypasses, and report trigger coverage separately.

Measure complete hidden-verifier success after the assigned fault; recovery within four subsequent tool calls; tool calls/tokens/time from failure to causal repair; repeated normalized command-plus-observation pairs without relevant state change; stopping with the fault unresolved; and a successful execution of the affected operation after its last substantive edit. Use all assigned opportunities as denominator, count timeouts/never-finishes as failures, and pair clean/faulted results on the same roots. Recovery must improve together with semantic success under identical budgets; more test calls or verbal verification claims are not mechanism evidence.

A prompt can explicitly prescribe inspect–repair–rerun. RS-SFT can include successful recovery trajectories. The plausible RL advantage is learning which action resolves its own encountered failure states under a limited budget, but that advantage over well-matched SFT is UNVERIFIED. Do not reward a recovery ritual, shorter traces, or test frequency. Preserve the council's strong prompt, inference-compute, continued-SFT and RL-success-imitation controls when the other roles finalize the arms.
